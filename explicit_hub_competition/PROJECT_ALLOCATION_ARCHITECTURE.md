# Project Allocation Architecture

## Baseline population

**Option L is selected.** Each region contains a beneficiary firm with one or more collaboration projects. The firm remains located in its home region but may use either open hub.

A common unlocated project pool is rejected because it would blur the distinction between intermediary choice and firm/project location competition.

## Sequence

1. Regional governments choose whether to provide Hub 1 and Hub 2.
2. Each beneficiary firm-project observes its own need/type and the broad partner-pool specialization of open hubs.
3. Where more than one hub is feasible, the project chooses the hub with the highest expected direct productive-match value.
4. The chosen hub searches its regional partner pool and partner-specific compatibility is realized.
5. If direct matching fails and the rival hub is open, the project may be referred to the rival's non-overlapping pool.
6. A successful collaboration changes the beneficiary firm's competitive capability and creates surplus for the matched complementary partner.
7. Beneficiary firms subsequently interact in the downstream product market.

## Literal project stealing

When both hubs can serve the same project need, opening Hub 2 can cause a project that would otherwise be mediated by Hub 1 to choose Hub 2 because `V_2(theta) > V_1(theta)`. This is project stealing generated by productive matching heterogeneity.

## No relocation

Hub choice does not move the beneficiary firm across regions. The collaboration link/partner allocation changes while the beneficiary firm's regional identity remains fixed. This distinction is essential for the later comparison with regional firm-location/public-input models.
