# Partner-Set Architecture

## Objects

Each public hub `i` is anchored to a regional ecosystem of complementary agents/resources represented by partner pool `S_i`.

A beneficiary firm-project has need/type `theta`. A potential partner `s` creates productive value `v(theta,s)` only when the resources/capabilities are sufficiently complementary. Mere contact is not productive collaboration.

## Overlap

`S_1` and `S_2` may contain different partners capable of satisfying the same class of project needs. Define the economically relevant overlap as the set of project needs for which both hubs can generate a positive direct productive match.

This is the matching-content interpretation of `S_1 ∩ S_2`.

For those projects, both hubs are feasible intermediaries and endogenous project allocation creates literal competition.

## Exclusive specialization

`S_1 \ S_2` and `S_2 \ S_1` denote partner capabilities/project needs effectively served by only one regional pool.

These non-overlapping capabilities prevent winner-take-all and provide the economic basis for cross-hub referral.

## Union and cooperation

When cross-hub referral is available, an unsuccessful first-hub search can gain access to the rival's non-overlapping partner capabilities. The feasible fallback opportunity set is therefore linked to `S_1 ∪ S_2`.

The union does not mean that the two hubs become one platform or that all users multihome. Referral is conditional routing after failed direct matching.

## Same-structure duality

The same pair `(S_1,S_2)` generates both forces:

- common feasible capability coverage -> competition for mediation of overlapping projects;
- exclusive capabilities -> gains from referral and cooperative routing.

No separate `-delta E_1E_2` or `+beta E_1E_2` term is required.
